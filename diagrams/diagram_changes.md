## 1. domain_class.puml（概念クラス図）

### 追加
- **アカウント**クラス（実装では予約にログイン必須。`requireCustomerAccount()`）。利用者と 1:1。
- **追加料金**クラス。予約 1 : 追加料金 *。
- ホテルに `地方 / 都道府県 / 市区町村 / 説明`（空室検索の地域絞り込みが依存）。
- 部屋に `部屋ID`（部屋番号はホテル間で重複するため識別子にならない）。
- 予約に `基本料金 / 支払済 / チェックイン日時 [0..1] / チェックアウト日時 [0..1]`。
- 請求に `基本料金 / 追加料金合計`。
- 支払いに `支払種別`。
- 関連: `ホテル 1 o-- * 部屋種別`（部屋種別はホテルごとに別インスタンス）、`予約 * -- 1 ホテル`（reservation.hotelId 直接保持）、`宿泊 * -- 1 部屋`（stay.roomId）。

### 変更
- `予約 0..1 -- 0..1 部屋` → `予約 * -- 0..1 部屋`：チェックアウト後も `assignedRoomId` が残るため、1部屋は過去の複数予約から参照される。旧版は概念図と設計図で多重度が食い違っていた。
- `宿泊 1 -- 0..1 請求`、`請求 1 -- 0..1 支払い` → **請求・支払いとも予約に直接接続**：実装では `invoice.reservationId` / `payment.reservationId` であり、宿泊・請求間のリンクは存在しない。
- `フロントスタッフ * -- * 宿泊` → `フロントスタッフ 1 -- 1 ホテル : 担当`：実装に宿泊担当者の記録はなく、代わりにスタッフアカウントはホテルごとに1つ（`hNNN-front`）で、担当ホテル以外の予約を扱えない（`assertStaffCanAccessReservation()`）。
- `予約システム管理者 1 -- * ホテル` → `* -- *`：管理者アカウント（admin 等）は全ホテルを管理できる（`hotelId: ""`）。
- 宿泊.実チェックアウト日時に `[0..1]` を付与（チェックイン中は空文字列）。

### 削除
- 予約システム管理者・フロントスタッフの `氏名`：実装ではログインIDとパスワードしか持たない。概念的には氏名があってもおかしくないので、チームで「概念図には残す」判断をしてもよい（その場合は変更点として説明できるようにしておく）。

## 2. design_class.puml（設計クラス図）

### バグ修正
- **旧版はクラス定義が `利用者`、関連の行だけ `顧客` になっており、PlantUML が空の「顧客」クラスを自動生成していた。** `利用者` に統一。

### 追加・変更（概念クラス図と共通の変更に加えて）
- `予約.料金() : int` を削除し、属性 `基本料金 : int` に置き換え：実装は予約確定時に `pricePerNight × 泊数` を **baseAmount として保存**する。後から管理者が料金表を変更しても既存予約の金額は変わらないため、派生操作ではなく保存済み属性が正しい表現。
  - ※概念クラス図で「/空室数 は派生」とした判断とは逆方向の結論になる点に注意。空室数は毎回計算（派生）、予約金額は確定時に固定（属性）、と使い分けの理由を説明できる。
- `予約.チェックインする(部屋 : 部屋)` → `チェックインする()`（引数なし）：実装 `checkIn()` はシステムが AVAILABLE な部屋を自動選択する。スタッフが部屋を指定する設計ではない。
- 旧版で設計クラス図から抜けていた `キャンセル日時 [0..1]` を復活（概念図・実装 `cancelledAt` と整合）。
- アカウントに `ログインする()` を追加（`loginUserAccount()` 対応）。
- `空室数(期間)` の計算式をノートで明記：「OUT_OF_SERVICE を除く部屋数 − 期間が重なる RESERVED/CHECKED_IN の予約数」（`availableRoomCount()`）。

## 実装側の問題として指摘しておくべき点（図は実装に合わせたが、要検討）

1. **支払い未完了のままチェックアウトを保留できない。** 計画書 UC5 の代替系列 A2「支払いが完了しない場合は CHECKED_IN のまま」は未実装で、実装は請求と支払いを常に同時作成する。図は実装に合わせたが、ユースケース記述（計画書）側とどちらに寄せるかチームで決める必要がある。演習6（新要件対応）の題材候補にもなる。
2. **ホテル編集で部屋種別・部屋を全削除して再登録するため、既存予約が参照する roomTypeId / roomId が消える可能性がある。** 編集画面で ID を変えると過去の予約が「不明な部屋種別」になる。保守フェーズの改善候補。
3. **チェックインが日付を検証しない。** チェックイン日より前でも RESERVED ならチェックインできる。図には反映していない（反映すると実装と乖離するため）が、口頭質問されうる。
4. **部屋の「状態」と予約の「期間重複」の二重管理。** 空室数は予約の期間重複で数え、部屋割当は status = AVAILABLE で判定している。設計クラス図のノートで計算式を明示したのはこのため。
5. パスワードが localStorage に平文保存される。講義課題としては許容範囲だが、レポートで「本番では不適切」と一言添えると良い。

## 複雑さについての判断

- クラス図は12クラス+列挙2つになった。**解説可能な上限に近い**が、実装のエンティティを全て網羅するにはこれが最小構成。発表時間が厳しい場合は、アカウント・追加料金を省いた「発表用抜粋版」を別途作ることを勧める（省いた事実と理由を口頭で言えるようにしておく）。
- 管理者のホテル編集フローは ui.js 側のロジックが大きく（行の動的追加・部屋種別セレクトの同期など）、アクティビティ図にすると UI 操作の記述だらけになるため作成しなかった。必要なら「入力→検証→保存」レベルに抽象化して作る。
